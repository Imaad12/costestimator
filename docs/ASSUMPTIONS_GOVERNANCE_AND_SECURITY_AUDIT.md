# Assumptions governance and security audit

Scope: the assumptions register (`assumptions`, `project_assumptions`), its workflow, its identity and approval controls, and what a database or application administrator can and cannot do undetected.
Method: code reading plus tests that try to break each control (`tests/closure/test_assumptions_governance.py`, `tests/closure/test_closure_scenario.py` stage `20_assumption_bypass_blocked`,
`tests/closure/test_negative_controls.py`, `tests/integration/test_actor_isolation_api.py`). Nothing below is claimed unless a test or a code line is cited.
This audit does **not** certify the application as production-secure; section 5 lists what is not assured.

## 1. Answers to the fifteen questions

| # | Question | Answer (evidence) |
|---|---|---|
| 1 | Where are assumptions stored? | SQLite only. Global library: table `assumptions` (one row per *version*). Project adoption / override: `project_assumptions`. The seed file `data/assumptions/assumptions_register.csv` is insert-only into the database (`refdata.load_assumption_register`: status *Pending Review*, **no value**, origin `seed`). Workbooks and `project.json` are generated views. A frozen estimate copies every resolved value into `estimate_snapshots` (`snapshots.build_snapshot`). |
| 2 | Which types are manually entered? | Library rows through `assumptions.create_assumption` (new: action `create_assumption`, REST/UI/CLI) and revisions through `revise_assumption`; project overrides through `set_override`. |
| 3 | Which are imported from files? | The seed CSV (insert-only, no values) and workbook round-trip *override proposals* (`excel/roundtrip.py`: only `set_override`, i.e. Pending Review; the status column in a file is ignored). |
| 4 | Which are generated by deterministic calculation? | None are written as assumptions. Calculated values (durations, labour-hours, allocations) are analysis output or governed-parameter inputs and are never stored as approved assumptions. The `origin` value `calculated` exists for a person to record a derived value; it follows the normal workflow. |
| 5 | Which can be proposed by AI? | None as register rows. `ai_suggestions` kinds are `mapping`, `clarifications`, `scope_gap`, `quote_extraction` (`services/suggestions.py`). `create_assumption` refuses an AI principal (`AI_FORBIDDEN`) and `origin='ai'` (tests). `app/ai` cannot import approval code (AST test `tests/approvals/test_ai_boundary.py`). |
| 6 | Which can be seeded by demo data? | The demo loader (`app/demo/build.py`) adopts assumptions and approves project overrides as the single `demo-seed` principal on a *demonstration* project; those approvals are recorded as `unregistered` and the project is flagged demo, so they never count for readiness. Four-eyes is relaxed only inside that loader and restored in a `finally` block. |
| 7 | Who can create / edit / approve / reject / supersede? | `policy.py`: create/edit/submit = Estimator, Procurement, Commercial, Administrator (write roles, never AI/Viewer); approve/reject = Estimator, Commercial Approver, Administrator **other than the author** (see Q14); supersede happens only as a side effect of approving a newer version. |
| 8 | Can an approved assumption be modified in place? | No. Service: `revise_assumption` on an approved row inserts a new Draft version (`supersedes_version` link). Database: trigger `trg_assumption_immutable` aborts any change to value, unit, name, source, evidence, creator, approver, synthetic flag or origin of an *Approved/Superseded* row, and any status regression (tests: six SQL statements refused with `IMMUTABLE_RECORD`; a superseded version cannot be resurrected). |
| 9 | Can it be deleted or its provenance replaced? | Not through the service (no delete function) and not through SQL while the triggers exist (`trg_assumption_nodelete`, `trg_assumption_immutable`). Same for project overrides (`trg_project_assumption_*`), productivity norms and workforce profiles. **Limit:** the triggers are a guard, not tamper-proofing: anyone with write access to the database file can drop them (section 4). |
| 10 | Can an AI-generated or synthetic assumption bypass review? | AI: no (Q5). Synthetic: a synthetic assumption follows the same workflow, but `data_class()` always reports *Explicitly synthetic test data* and `readiness._closure_gate` refuses production readiness while a synthetic assumption feeds the estimate. Approval of a synthetic value never turns it into "verified". |
| 11 | Versioned, auditable, linked to estimates and snapshots? | Versioned: `(id, version)` unique, `supersedes_version`, status lifecycle. Audited: `audit.log` for create/edit/submit/revise and `approvals.record` (approval row + hash-chained audit row) for decisions; `assumption_history()` returns versions, approvals and audit events. Linked: `estimate_snapshots.snapshot_json["assumptions"]` stores id, value, status, origin and version of every value the estimate used; replay reads the snapshot only (stage 25/26 and `tests/unit/test_full_replay.py`). |
| 12 | Can global assumptions silently alter existing projects? | A project that adopted an assumption *without* an override follows the approved global default by design - the estimate result changes on the next calculation, and the change is visible (new approved version, approval record). **Frozen estimate versions do not change**: replay uses the snapshot (closure stage 25 revises a global assumption and a global rate after the freeze; frozen totals and every printed document figure are unchanged). A project override never edits the global library (`tests/closure/test_assumptions_governance.py`). |
| 13 | Are write operations protected consistently across UI, REST and CLI? | All three call `app/api/actions.py` / the same services; permission and four-eyes checks are inside the services (`approvals.authorize`). Tests: REST viewer 403, estimator self-approval 409 `SELF_APPROVAL_BLOCKED`, unauthenticated 401, request-body `reviewer`/`actor` fields ignored (identity comes from the token); CLI `action` as a Viewer exits 1 `PERMISSION_DENIED`, as an unknown user `AUTH_REQUIRED`. |
| 14 | Can a user forge an approver identity, change a role or bypass approval through direct API calls? | The API derives the actor from the signed token/session (`api/deps.py`), never from the body. Users are created by an Administrator through the API action `create_user` (audited with the creator) or by whoever has *shell access* through `python -m app.cli create-user` (unauthenticated by design; now audited as `cli:<operating-system user>`, including `--reset` password resets, which were previously not audited). There is **no role-change service**: changing a role or actor type needs direct database access. A *service-level* call with a hand-built `Actor` (in-process code) is trusted by the services, but its approval is **recorded** as `unregistered` / `role_mismatch` / `test` from the users table (`approvals.resolve_actor_type`) and `readiness.check_approval` rejects it; test: a forged "Commercial Approver" approves an assumption, the row says `actor_type=unregistered` and does not count. **Default changed in this iteration:** four-eyes is now the default (`allow_self_approval=false` in code and `config/settings.toml`), and an Administrator is not exempt for assumptions, project overrides, productivity norms, workforce profiles, programme baselines, tender queries, tender documents and rates (`policy.SEPARATION_ENTITIES`). |
| 15 | Can a DB admin or application admin alter assumptions or audit records without detection? | **Partly.** The audit log is hash-chained (`audit-verify`): editing or deleting an audit row breaks the chain from that row on and is detected. But the chain is tamper-*evident*, not tamper-*proof*: a person with write access to the file can rewrite the whole chain consistently from the first altered row, drop the immutability triggers, edit an approved value and re-hash. Nothing in the file is signed with a key held outside the database. An application Administrator can register users (including a user typed `human`; audited, not separated). Whoever has shell access to the machine can run the CLI (create user, reset a password) or edit the database directly - local shell access is full control by design. See section 5. |

## 2. What changed in this iteration

* Register extended: `category` (17 governed categories), `origin` (manual / import / seed / calculated / ai / synthetic), `reason`, `business_impact`, `uncertainty`,
  `consequence_if_missing`, `affects`, `reviewed_by/at`, `supersedes_version` (migration `0015`).
* `data_class()` / `evidence_report()` / report `assumption_evidence`: every adopted or mandatory assumption is classified as *Verified source data*, *Company-approved internal data*,
  *Project-approved data*, *Imported but unverified*, *Pending human review*, *AI-proposed data*, *Explicitly synthetic test data* or *Missing data* (priority: synthetic, then missing, AI, pending, approved).
  "Verified source data" requires a manual origin, evidence and Medium/High confidence **and** approval; synthetic values never reach it.
* Database guards (triggers) on `assumptions`, `project_assumptions`, `productivity_norms`, `workforce_profiles`.
* Four-eyes default and Administrator non-exemption for material records.
* Readiness gate (Stage J): a synthetic assumption feeding the estimate blocks production readiness; unapproved adopted assumptions remain reconciliation findings (High) that only a registered human
  Commercial Approver can accept as a recorded exception.
* Backups include the new tables (`KEY_TABLES`, project export), and the triggers survive restore (test).

## 3. Workflow and states

`Draft → Pending Review (submit) → Approved | Rejected → Superseded`. Manual entry is never approval (`status='Draft'`). Editing a Draft/Pending/Rejected row edits it in place and returns it to Draft;
editing an Approved row creates version n+1 (Draft) and leaves n Approved until n+1 is approved by another person. A project-specific approved override lives in `project_assumptions` and never touches the library.

## 4. Threat model and limits

| Threat | Control | Residual risk |
|---|---|---|
| Honest user mistake edits an approved value | service refuses; trigger aborts | none known |
| Malicious application user (non-admin) | role checks, four-eyes, token identity, audit | collusion of two registered users |
| Application Administrator | audited user/role changes; not exempt from four-eyes for material records | can create a second user typed `human` and use two accounts; no MFA; no separation of administrator duties |
| Person with write access to the SQLite file | hash chain detects naive edits; backups validated by hash | can rewrite the chain and drop triggers undetected; the file is not encrypted or signed |
| Stolen session / token | HMAC-signed, 12 h TTL, same-origin check on cookie writes, lockout after 5 failures | no MFA/SSO, no IP binding, no revocation list beyond user deactivation |
| Test/synthetic data presented as real | actor type, environment, project class, synthetic flags, banners, validator | a human can still *mislabel* a real project `is_demo=1` or a real user `test` - that only makes the output *less* trustworthy, never more |

## 5. Not assured (do not claim)

MFA, SSO, enterprise identity assurance, immutable/off-box audit storage, encryption at rest, separation of administrator duties, a signed audit anchor, rate limiting on the API beyond sign-in lockout,
penetration testing. The product is a **local-first single-site tool** (`docs/SECURITY.md`): bind it to localhost or a trusted LAN behind TLS; do not expose it to the internet.

## 6. Hardening backlog (ordered)

1. Anchor the audit chain head outside the database (signed daily export; or append-only WORM storage) and verify it on startup.
2. Separate administrator duties: user-admin, role-admin and data-admin; require two administrators to create a `human` user or change a role.
3. MFA/SSO for sign-in; remove password sign-in for approvers.
4. Encrypt the database file and backups; key management outside the repository.
5. Refuse to *record* an approval from an unregistered/mismatched actor in a production environment (needs a `db` handle in `authorize`; deferred because the whole test suite and the demo use unregistered actors).
6. Per-entity approval limits (value thresholds beyond supplier selection) and mandatory review of every Critical-path assumption before final estimate approval.
7. Independent penetration test before any wider deployment.
